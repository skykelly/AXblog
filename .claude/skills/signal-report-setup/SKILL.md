# 고정 질문 리서치 리포트 — 새 프로젝트 만들기

주제 하나를 "고정 질문 → 주기적 재조사 → 4유형 기록(지표·사건·해석·전망) → 아티클과 Diff → 포털"로 운영하는 프로젝트를 처음부터 세운다. 회차 실행은 `signal-report-round`, 자료 수동 입력은 `signal-report-intake` 스킬이 맡는다.

참조 구현: 공개 저장소 `https://github.com/skykelly/axblog` (AX Signals). 같은 구조를 새 주제로 옮기는 것이 이 스킬의 일이다. 코드를 새로 짜지 말고 이 저장소를 읽기 전용으로 받아 필요한 파일을 복사·수정한다.

## 핵심 원칙 (모든 단계에 적용)

- **원본은 하나:** 질문별 `records.jsonl`만 원본이다. 아티클·Diff·변경 이력·포털은 언제든 다시 만드는 결과물이다.
- **근거와 판단의 분리:** 지표·사건은 원문 링크를 갖고, 해석·전망은 사실 기록 번호(`basis`)에 연결한다.
- **본 조사는 백지에서:** 딥리서치는 이전 글을 보지 않는다. 이전 기록과의 대조는 그다음 단계에서 한다.
- **비교 가능성:** 질문과 함께 추적 지표 목록을 고정한다. 질문·지표는 분기에 한 번만 바꾸고, 바꾸면 버전을 올린다.
- **출처 등급:** A = 1차 조사·공식 발표·정부 통계, B = 주요 언론·2차 보도·컨설팅, C = 블로그·출처 불명. C는 단독 근거로 쓰지 않는다.
- **단정 금지:** 원문을 직접 열지 못한 값, 정의가 다른 값, 확신이 낮은 값은 단정하지 않고 `check_flags`에 '확인 필요'를 남긴다.

## 0. 먼저 정할 것 (AskUserQuestion으로 한 번에)

1. 주제와 독자: 누가 무엇을 판단하려고 읽는가
2. 카테고리 수(1~4)와 이름, 질문 번호 접두어(예: H1~, F1~)
3. 저장 위치: 새 GitHub 저장소(이름) 또는 연결된 로컬 폴더. 공개 저장소면 남의 글 전문·사내 자료를 커밋하지 않는다는 점을 알린다
4. 포털 필요 여부와 브랜드 색(없으면 중립 팔레트)
5. 주기: 기본은 딥리서치 질문당 월 1회 + 간단 조사 매주. 실행 요일·시각
6. 지역 렌즈: 한국 중심인지, 글로벌 선행 + 한국 확인인지

대답이 없으면 기본값으로 진행하고, 무엇을 가정했는지 첫 보고에 적는다.

## 1. 질문 설계 (사용자 승인 필수)

카테고리마다 고정 질문 3~6개. 각 질문에 아래를 정한다.

| 항목 | 규칙 |
|---|---|
| 질문 | 상태를 묻는 한 문장. "어디까지 왔는가", "무엇이 늘고 줄었는가", "누가 주도하는가" |
| 한 줄 답 형식 | 매 회차 같은 틀로 답하게 하는 형식 (예: 단계 판정, 순위, 방향×속도) |
| 판정 척도 | 질문 성격에 맞게 고른다 (아래) |
| 판정 기준표 | 단계마다 뜻, 수치 기준, 인정하는 근거. 간접 근거로 판정한 칸은 '잠정' |
| 추적 지표 5~10개 | ID `질문-T1~`, 이름, 단위, 정의, 우선 출처, 발표 주기 |

판정 척도 고르기:
- 기술·서비스 확산형: 채택 4단계(실험·얼리어답터·확산·주류), 수치 기준 10/25/50%
- 인구·가구·생활 통계형: 방향(증가·정체·감소) × 속도(가속·유지·둔화), 기준은 최근 3~5년 추세 대비
- 수요·원인형: 영향 순위(1~N위)와 순위 변동
- 경쟁·주도권형: 접점별 주도 주체 지도

통계 주제는 공식 통계의 발표 시기를 지표 표에 적어 두고, 해당 월 회차에서 먼저 찾게 한다. 발표 시기는 기억으로 쓰지 말고 조사해서 적는다.

예시 (한국인의 거주 형태·가족·생활 변화, 초안): 거주 형태가 어떻게 바뀌는가(자가·전월세·1인 주거·공유 주거), 가족 구성이 어떻게 바뀌는가(1인·부부·한부모·비혼 동거·다문화), 생활 사건의 시기와 빈도가 어떻게 바뀌는가(독립·혼인·출산·은퇴·돌봄), 하루의 시간과 생활 방식이 어떻게 바뀌는가(맞벌이·재택·가사 외주화), 그 변화가 어떤 새 수요를 만드는가. 실제 질문은 사용자와 확정한다.

질문·지표·기준표를 표로 보여 주고 승인을 받은 뒤에만 다음 단계로 간다. 이후 바꾸기 비싼 결정이기 때문이다.

## 2. 저장소 뼈대

1. 참조 구현을 읽기 전용으로 받는다: `GIT_LFS_SKIP_SMUDGE=1 git clone --depth 1 https://github.com/skykelly/axblog` (작업 폴더 밖, 스크래치 위치).
2. 새 프로젝트로 복사해 고친다.
   - `lib/records.py` (변경 종류 KIND_ORDER, patches 적용), `lib/judge.py` (게이지·판정 기준표 부품 — 판정 척도를 새 주제에 맞게 바꾼다), `lib/article.css`
   - `site/` (`build_site.py`, `changes.py`, `menu.py`, `portal.py/js/css`, `article_ui.html`, `chat.html`, `catalog.json`) — 제목·소개 문구·색·카테고리를 새 주제로
   - `tools/intake.py`
   - `.claude/settings.json`: WebFetch·WebSearch·Agent 허용
3. 질문 폴더 `카테고리/질문id/`: `request_r1.md`, `build_records.py`, `records.jsonl`, `render_article.py`, `signal_r1.json`, `patches.jsonl`(빈 파일)
4. `README.md`: 주제 표, 질문 번호 규칙, 운영 원칙, 회차 흐름, 포털 주소
5. `CLAUDE.md`: 판단 규칙(출처 등급, 단정 금지, 아티클엔 사실과 기준만, 문장 수정 시 revisions, 반영 후 절차, 보고 형식)과 수동 입력 절차. 참조 구현의 CLAUDE.md를 주제에 맞게 고친다
6. 카테고리별 `README.md`: 질문 표(번호·질문·한 줄 답 형태·상태)와 질문별 진행 상황

## 3. 기록 형식 (records.jsonl 한 줄 = 한 기록)

공통: `question, question_version, id(질문-M/E/I/F-NNN), type(지표|사건|해석|전망), importance(1~3), statement(한 문장), first_seen, last_seen(R번호), status(유효|미확인|대체됨|반박됨), replaces, check_flags[], sources[{url,publisher,date,grade}], verified, revisions[{on,kind,before,why}]`

- 지표: `indicator(T번호), value, unit, as_of, region, definition, prev_value, representative`
- 사건: `date, actor`
- 해석: `target, direction(강화|약화|중립), basis[]` — basis 없으면 저장하지 않는다
- 전망: `due, condition, method(관찰 가능한 판정 방법), basis[], forecast_status(진행 중|적중|빗나감|만료), result` — due·method 없으면 저장하지 않는다

`build_records.py`가 규칙을 검증한다(근거 연결, ID 중복, 출처 등급, 변경 종류). 실패하면 기록을 고친다.

## 4. 기준 회차 R1

`signal-report-round` 스킬의 "딥리서치 회차"를 R1로 질문마다 실행한다. 질문 수가 많으면 질문별 하위 에이전트로 병렬 처리하고, 각 에이전트에는 그 질문의 요청서 전문과 기록 형식, 출처 규칙을 넘긴다. 끝나면 우선 카테고리에 검증 탐침(백지 재조사 → 대조)을 한 번 돌린다.

## 5. 포털

1. `python3 site/build_site.py` — 깨진 내부 링크 0이어야 통과.
2. Artifact 도구로 새 주소에 게시: 진입 페이지 `site/dist/artifact_index.html`, 아티클 페이지는 `site/dist/manifest.json`의 pages를 같은 경로로 함께 올린다. 첫 게시 주소를 README와 CLAUDE.md에 적는다.
3. 포털 AI 질의응답을 넣으면 `sample` 기능을 선언한다(보는 사람의 Claude 사용량). 이후 재게시에서는 `capabilities`를 생략해 유지한다. `{}`를 넘기면 꺼진다.
4. PC 폭과 폰 폭 화면을 직접 확인한다.

## 6. 정기 실행 등록

예약 작업 도구로 두 개를 만든다 (사용자에게 시각 확인).
- 주간 간단 조사: 매주 정한 요일·시각. 프롬프트는 "저장소를 붙이고 CLAUDE.md를 읽은 뒤 signal-report-round의 주간 간단 조사를 실행"처럼 단독으로 이해되게 쓴다.
- 월간 딥리서치: 질문을 주마다 1~2개씩 나눠 돌리는 순환표를 README에 적고, 예약 작업은 "이번 주 순번의 질문을 딥리서치 회차로 실행"하게 한다.
각 작업이 어떤 승인 모드로 등록됐는지 한 문장으로 알린다.

## 7. 보고

질문 수, 질문별 기록 수(지표·사건·해석·전망), 추적 지표 확보율, '확인 필요' 건수, 포털 주소, 예약 작업 시각, 가정한 기본값.

## 지난 프로젝트에서 배운 함정

- 마크다운 굵게: 닫는 `**` 앞이 문장부호이고 뒤가 한글이면 렌더되지 않는다. 문장부호를 굵게 밖으로 뺀다.
- `10~20%(1,900억~3,850억)`처럼 물결표가 두 번 나오면 취소선이 된다. 렌더러에서 단일 `~`를 이스케이프한다.
- 표 칸의 한글 단어가 한 글자씩 끊기면 `word-break:keep-all; overflow-wrap:break-word`.
- 게시가 "다른 세션이 더 새 버전을 올렸다"며 거부되면, 저장된 최신본 위에 내 변경을 합쳐서 다시 게시한다. 덮어쓰지 않는다.
- 정기 실행과 수동 작업이 같은 저장소를 고치므로, 작업 전 항상 `git pull`.
- 경영진·외부 공유용 문장은 짧은 보고체, 줄표로 문장 잇지 않기, 비유·과장 없음, 약어는 처음에 풀어 쓰기.
