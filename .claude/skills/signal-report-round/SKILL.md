# 고정 질문 리서치 리포트 — 회차 실행

`signal-report-setup`으로 만든 프로젝트(참조 구현: skykelly/axblog)에서 쓴다. 시작 전에 저장소 루트의 `README.md`, `CLAUDE.md`, `site/catalog.json`, 대상 질문의 카테고리 `README.md`와 최신 `request_rN.md`를 읽는다. 프로젝트 문서의 규칙이 이 스킬과 다르면 프로젝트 문서를 따른다. 작업 전 `git pull`.

세 가지 모드가 있다. 요청이나 예약 작업이 어느 모드인지 정한다.

| 모드 | 언제 | 만드는 기록 | 아티클 |
|---|---|---|---|
| 딥리서치 회차 | 질문당 월 1회 (순환표) | 4유형 모두 | 새 회차 `article_rN.html` |
| 주간 간단 조사 | 매주 | 지표·사건 추가·갱신, 전망 판정 결과 | 새로 쓰지 않고 현재 회차를 갱신 |
| 검증 탐침 | 기준 회차 직후, 이후 분기마다 또는 요청 시 | 기록을 바꾸지 않고 보고서만 | 없음 |

## A. 딥리서치 회차 (R번호 +1)

1. **요청서 `request_rN.md`:** 고정 질문, 한 줄 답 형식, 조사 기간(직전 회차 이후 + 지표는 최신 공개값), 추적 지표 표, 출처 기준, 미확인 단서(`python3 tools/intake.py leads 질문`)를 넣는다. **이전 아티클과 이전 판정은 넣지 않는다.**
2. **딥리서치:** 질문 하나에 하위 에이전트 하나. 요청서 전문을 넘기고, 출처 링크가 달린 보고서를 받는다. 보고서는 회차 자료로 보관(공개 저장소면 요약만).
3. **4유형 추출과 원문 확인:** 보고서를 기록으로 쪼갠다. 지표·사건은 원문을 다시 열어 수치·날짜가 실제로 있는지 확인하고 `verified`를 채운다. 확인 못 하면 단정하지 않고 '확인 필요'. 해석은 basis, 전망은 due·condition·method·basis가 없으면 버린다.
4. **DB 대조와 점검 (초안을 쓰지 않은 별도 에이전트):**
   - 새 기록과 기존 기록 짝짓기: 지표는 T번호·지역·정의, 사건은 주체·일자·내용, 해석은 대상·방향. 뜻이 같으면 새로 만들지 않고 `last_seen`만 올린다
   - 빠진 중요 사실: 중요도 2 이상 유효 기록이 이번 보고서에 없으면 보완 조사 대상
   - 모순된 해석: 이전과 반대 방향인데 새 근거가 없으면 이전 해석 유지 + '해석 흔들림' 플래그
   - 수치 충돌: 같은 지표 다른 값 → 둘 다 기록, 등급 높은 쪽을 대표값
   - 근거 없는 전망: 저장하지 않음
   - 만기 전망: method대로 적중·빗나감·만료 판정
5. **보완 조사:** 위에서 나온 빈 곳만 짧은 검색으로 확인. 딥리서치를 다시 돌리지 않는다.
6. **기록 반영:** `build_records.py` 갱신 → 실행(규칙 검증 통과). 바뀐 문장은 `revisions`에 이전 문장과 이유, 변경 종류는 `lib/records.py`의 KIND_ORDER(누락정정, 단정반증, 전망 교체, 판정 기준 보완, 상충, 전망 점검, 갱신, 신규)만 쓴다.
7. **판정과 아티클:** 판정 기준표로 다시 판정하고 `signal_rN.json`(칩·게이지)을 낸다. `render_article.py`로 아티클 생성. 순서: 한 줄 답 → 해석 → 주요 사건 → 전망 → 판정 → 핵심 지표 → 미확인·경고. 문장마다 근거 기록 번호. 본문에는 사실과 기준만 쓰고 "검증 결과에 따르면" 같은 과정 문구는 넣지 않는다.
8. **Diff:** 기록의 `added_on`, `revisions`, 상태 변화에서 자동 생성된다(`site/changes.py`). 맨 위에 이번 회차 가장 중요한 변화 3가지를 둔다.
9. **마무리:** 카테고리 README 진행 상황 갱신 → `python3 site/build_site.py`(깨진 링크 0) → PC·폰 폭 화면 확인 → 커밋 → 포털 재게시.

해석·전망·판정은 딥리서치 회차에서만 바꾼다. 판정이 매주 흔들리지 않게 하기 위해서다.

## B. 주간 간단 조사

질문마다 짧은 검색으로 다음만 처리한다.
- 값이 빈 추적 지표, 이번 주 발표된 공식 통계(지표 표의 발표 시기 참조)
- 원문 미확인(C등급) 사건의 원문 찾기
- due가 지난 전망 판정
- 수동 입력 단서(leads)
- 지난 회차 이후 새로 일어난 큰 사건(출시·제도·발표)

반영은 지표·사건 기록 추가·갱신과 전망 판정 결과뿐이다. 해석과 판정은 바꾸지 않고, 판정에 영향이 갈 만한 것은 '확인 필요' 플래그와 다음 딥리서치 요청서 메모로 남긴다. 그다음 render → build_site → 커밋 → 게시. 바뀐 것이 없으면 "변화 없음"과 검색 범위를 보고하고 게시는 건너뛴다.

## C. 검증 탐침

1. 질문마다 하위 에이전트가 기록을 보지 않고 같은 요청서로 백지 재조사 → `probe_YYYYMMDD/blind_질문.md`
2. 다른 에이전트가 백지 결과와 기록을 대조해 `findings_질문.jsonl`: `{cls(변경 종류), ref(기록 ID), importance, impact(판정 영향|문장 수정|참고), statement, note, sources}`
3. `verification_report.md`: 판정 영향 → 문장 수정 → 참고 순서, 항목마다 출처 등급과 확인 범위
4. 기록은 바꾸지 않는다. 보고서를 사용자에게 보여 주고 승인한 항목만 다음 반영 때 적용한다(프로젝트 CLAUDE.md가 다르게 정했으면 그대로).

## 하위 에이전트 지시서에 반드시 넣을 것

- 요청서 전문, 기록 형식(필드·ID 규칙), 출처 등급 정의
- 원문을 직접 연 것만 verified, 수치·날짜를 지어내지 않기
- 결과 반환 형식(보고서 마크다운 또는 jsonl)과 파일 경로
- 다른 파일은 고치지 않기, 커밋·게시 금지(본 세션이 한다)
