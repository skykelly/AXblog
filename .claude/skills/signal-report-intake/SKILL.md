# 고정 질문 리서치 리포트 — 수동 자료 입력

사용자가 대화로 준 자료(기사, 보고서 파일, 링크, 다른 AI의 딥리서치 결과, 메모, 문장 지적)를 프로젝트 기록에 넣는다. 도구는 프로젝트의 `tools/intake.py`(참조 구현: skykelly/axblog). 시작 전 `CLAUDE.md`의 수동 입력 절차와 `site/catalog.json`을 읽고 `git pull`.

기본 모드는 **검토 후 반영**이다. 사용자가 "바로 반영"이라고 할 때만 검토 카드를 건너뛴다.

## 절차

1. **보관:** `python3 tools/intake.py stage 파일 --title .. --slug 영문 [--author --date --url --grade]`
   - 원본은 `inbox/`(git 제외)에만 둔다. 공개 저장소에는 남의 글 전문이나 사내·비공개 자료를 커밋하지 않는다.
   - 붙여 넣은 텍스트는 먼저 파일로 저장한 뒤 stage한다.
2. **주장 추출과 질문 매핑:** 자료의 주장을 한 문장씩 뽑아 catalog의 질문에 붙인다. 어느 질문에도 안 맞으면 "범위 밖"으로 표시한다.
3. **기존 기록 대조:** 주장마다 일치(재확인) / 갱신 / 상충 / 신규로 나눈다.
4. **원문 확인:**
   - 자료가 C등급이거나 URL이 없으면 주장마다 원문(A·B)을 찾는다. 확인된 범위만 기록 문장으로 쓴다.
   - 사용자 메모·관찰은 사실 기록이 아니라 단서(lead)로 받는다. 원문을 찾으면 기록으로 올린다.
   - 다른 AI의 딥리서치 결과도 같은 기준이다. 인용된 원문을 다시 열어 확인한다.
   - "이 문장 틀렸어" 같은 지적은 근거를 확인한 뒤 누락정정·단정반증으로 반영한다.
5. **후보 작성:** `intake/ID.proposal.json` 항목:
   - 수정: `{n, q, op:"revise", id, kind, why, set, add_sources, add_flags, add_basis, impact, claim, status}`
   - 추가: `{n, q, op:"add", record:{전체 기록}, impact, claim, status}`
   - 단서: `{n, q, op:"lead", claim, reason}`
   - `kind`는 KIND_ORDER(누락정정, 단정반증, 전망 교체, 판정 기준 보완, 상충, 전망 점검, 갱신, 신규)만. `impact`는 판정 영향 | 문장 수정 | 참고. 원문 전문은 넣지 않는다.
6. **검토 카드:** `python3 tools/intake.py preview ID` 결과를 채팅에 그대로 보여 주고 승인을 받는다. 판정 영향 항목을 맨 위에 둔다.
7. **반영:** `python3 tools/intake.py apply ID [--only 1,2 | --skip 3]` → 질문별 `patches.jsonl`에 쓰이고 `build_records.py`가 마지막에 적용한다. 출력의 "아티클에서 확인할 곳"을 보고 `render_article.py` 문장을 맞춘다.
8. **마무리:** render → `python3 site/build_site.py`(깨진 링크 0) → PC·폰 폭 확인 → 커밋 → 포털 재게시(capabilities 생략). 변경 이력에는 '제공 자료'로 표시된다.
9. **추적:** `intake.py list`(접수 목록), `intake.py leads [질문]`(미확인 단서 — 다음 회차 요청서에 넣는다).

## 판정에 영향이 갈 때

수동 입력으로 해석이나 판정이 바뀔 만하면 바로 바꾸지 않는다. 근거 기록만 넣고 '확인 필요' 플래그를 단 뒤, 다음 딥리서치 회차 요청서 메모로 넘긴다. 사용자가 즉시 반영을 원하면 판정 기준표에 비춰 근거를 보여 주고 승인을 받는다.

## 보고

접수 ID, 추출 주장 수, 반영·건너뜀·단서 건수, 질문별 변경, 판정 영향 여부, 남은 '확인 필요' 목록, 포털 갱신 여부.
